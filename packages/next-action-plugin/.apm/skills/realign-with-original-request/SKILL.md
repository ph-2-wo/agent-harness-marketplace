# 当初の要求に立ち返って直近の要求を読み直す

直近の要求は、当初の要求の言い換えであることが多い。
新しい要求として扱うと、当初の要求を外していた自分の側の誤りが見えない。

出力は次の5節を、この順で、見出しを付けて返す。

## 1. 要求を書き出す

当初からの要求を、古いものから全部、番号を振って書き出す。

- 出所は原文だけにする。依頼書、そのセッションのトランスクリプト、作業の記録に残したユーザーの言葉
- 1件ごとに出所（日付・ファイル）を添える
- 自分の解釈で言い換えない。要約するなら原文の語を残す
- 直近の要求も最後に入れる

## 2. 現状を書き出す

1 の番号ごとに、今どうなっているかを事実で書く。

- 数字・日付・件数で書く。「概ねできている」のような評価語を使わない
- 満たしているものも書く。満たしていない要求だけ拾うと、当たり前の部分が見えなくなる
- 番号ごとの受け皿（済み・A・R・D・無い）は `instruction-coverage-check` で出す
- 自分がこれまで書いてきた説明は、`explanation-evidence-review` で根拠を確かめてから使う
- 2つは同時に呼ぶ。どちらもサブエージェントが裏で動き、結果は後から届く

## 3. ギャップを書き出す

1 の番号ごとに、要求と現状の差を書く。

- 差が無いものは「無い」と1語で書く
- 差があるものは、何が要求で何が現状かを対にして書く
- 差を生んだのが自分の判断なら、いつ何を決めたかを添える
- 差を生んだのが、既にある指示やスキルを守らなかったことなら、その文面を引いて書く。それを原因として先に答え、手順書を直す案はその後に出す

## 4. 直近の要求をギャップから理解する

直近の要求が、1 のどの番号の言い換えかを特定する。

- 直近の要求の各語（例: 利益、工夫、当たり前）を、当初の要求の語に対応させる
- 3 で見つけた自分の判断のうち、直近の要求が指しているものを名指しする
- 「ユーザーが新しく要求した」と書くのは、1 のどの番号にも対応しないと確かめたときだけ

## 5. 本来やるべきだったことをネクストアクションにする

直近の要求に対して、4 の理解の上で本来やるべきだったことを、`create-next-action` に従って登録する。

- 2 で呼んだ2つの結果が届くまで、5 を出さない
- `instruction-coverage-check` で無いになった指示も、ここで登録する
- `instruction-coverage-check` で食い違いになった受け皿は、取り下げるか直して出し直す
- `explanation-evidence-review` で根拠不足・食い違いになった説明は、調べて直すか訂正してから出す
- 自分の役割の範囲で書く。他の主体（他のエージェント・ユーザー）の代わりに手を動かす案は入れない
- やらないことも1〜2行で添える。役割の外だと理解したことの証明になる

## 守ること

- 1〜3 で、原文に無い前提を足さない。質問の形でも足さない
  （「現実に持っていく意図か」のような問いは、原文に無い前提を持ち込む）
- 5 を出す前に止まらない。行動が無い理解は、理解したことにならない
