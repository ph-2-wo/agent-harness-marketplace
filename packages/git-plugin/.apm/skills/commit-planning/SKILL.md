# Commit Planning

完成した実装を、変更理由と依存関係に基づくCommitへ分割する。

Commitのために実装を変更しない。

## 1. 差分を構造化する

最終的に実現する動作を確認する。

その動作に必要な変更を、次の観点で整理する。

- 型
- 独立した部品
- 既存機能の拡張
- 部品間の接続
- test

各変更について、変更理由、利用元、依存先を確認する。

file種別や差分量だけで分類しない。

## 2. Commit境界を決める

次の変更を分離候補にする。

- 独立した変更理由を持つ
- 単独で成立し、reviewできる
- 後続Commitが自然に利用する前提になる
- 分離するとreview観点や検証内容が明確に変わる

次の変更はまとめる。

- 同じ目的に属する
- 単独の利用価値がない
- 分けてもreview観点や検証内容が変わらない
- file、型、layerが異なるだけである

準備Commitを依存順に置き、最後に機能をend-to-endで接続する。

testは対象の振る舞いを成立させるCommitへ含める。

分割のために実装変更が必要なら、実装を変えずCommitを大きくする。

各Commitについて次を示す。

- 目的
- 含む変更
- 先行Commitとの依存
- 確認内容

## 3. PR分割を検討する

独立した目的を持つトピックが複数ある場合、PR分割候補を提示する。

候補にはPRごとの目的、変更所属、依存関係を含める。

複数CommitであることだけをPR分割理由にしない。

branch操作とPR作成は行わない。

## 4. Human合意を得る

Commit列とPR分割候補を提示する。

合意前にCommitを開始しない。

## 5. Commitを作成する

合意した所属に従ってstageする。

Commit前にstaged diffが計画した内容だけを含むか確認する。

実装fileは編集しない。

実装変更が必要なら停止し、理由と変更案を示して再合意する。

hookなどによる予期しない変更を見つけた場合も停止する。

合意なしに変更やrollbackをしない。

## 6. 確認する

- 各Commitが計画した目的だけを含むか確認する。
- Commit前の変更が最終Commit列へ残っているか、最終diffで確認する。
- worktreeに取りこぼしがないか確認する。
- 計画したtest、lint、typecheckを実行する。

問題が判明した場合は、その失敗に必要な規則だけを追加する。
