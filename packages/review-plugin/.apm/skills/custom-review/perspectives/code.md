# プログラムのコードの観点

## 数値

### 異常な値が、普通の値に化ける

when

- 計算結果に下限・既定値・丸めをかける式を書いている
  - `Math.max` / `Math.min`
  - `||` / `??` の既定値
  - `toFixed` / `Math.round`
  - など
- 欠けたデータや対象外のデータを飛ばす分岐を書いている
  - `continue`
  - `filter`
  - `catch` での読み飛ばし
  - など
- など

then

- 異常が、普通の数値に見えないかを確かめる。例:
  - `Math.max(1, x)` で、全部 0 のときも 1 になる
  - 欠落を警告した後も、計算を続ける
  - 小さな値が丸めで 0 になる
  - など
- 出せないときは、出せないと示させる

事例

- 日ごとの目安の数が、保存の不具合で全日 0 になっていたのに、`Math.max(1, med)` で 1 に丸められ、正常に見えて気づけなかった
- 入力の値が欠けたまま計算を続け、-89% のような数字を出した

## 集計

### データの最初・最後を、本当の端とみなす

when

- 最初・最後・最小・最大を取る式を書いている
  - `MIN` / `MAX`
  - `[0]` / `at(-1)`
  - など
- 特定の種類の記録があるかどうかで数える条件式を書いている
- 集合に、後から要素（種類・対象・項目）を足している
- など

then

- データが途中から始まる・途中で切れる・その要素がまだ無かった時点を含むときにも、正しいかを確かめる

コード例

```
-- NG: 期間で絞った後の MIN は「期間内の最初」で、本当の開始ではない
SELECT session_id, MIN(ts) FROM events
WHERE ts >= ? GROUP BY session_id;

-- OK: 開始は絞る前に取り、期間は後で絞る
SELECT session_id, MIN(ts) FROM events
GROUP BY session_id HAVING MAX(ts) >= ?;
```

事例

- 期間で絞った後に `MIN` を取り、セッションの本当の開始時刻が分からなかった
- 「起動」を `session_start` の記録の有無で数え、記録が途中から始まるセッションを数えられなかった
- 最終章の終わりを字幕の最後の行で決め、動画の尺とずれた
- 集計の種類を後から足したら、それが無かった過去日の計算で処理が落ちた

### 割る・比べる対象が揃っていない

when

- 割り算・比較で、平均・率・順位を出す式を書いている
- など

then

- 分子と分母、比べる2つが、同じ定義の集合・同じ長さかを確かめる

コード例

```
-- NG: 分子と分母が別の条件
SELECT (SELECT SUM(duration) FROM sessions WHERE started_at >= ?)
     / (SELECT COUNT(*) FROM sessions);

-- OK: 同じ集合から取る
SELECT SUM(duration) / COUNT(*) FROM sessions WHERE started_at >= ?;
```

事例

- 平均時間の分子と分母を別の条件で取り、対象がずれた
- 長さの違う区間を、長さで割らずに合計で比べていた

### 自動処理でも動く値で、活動を判定する

when

- 活動・稼働・鮮度の条件式に、次の値を使っている
  - commit の有無・件数
  - ファイルの更新日時（mtime）
  - 最終更新
  - など
- など

then

- 自動処理や他人の操作でもその値が動かないかを確かめ、動くなら除外の条件を入れさせる

コード例

```
# NG: 起動 hook が自動で入れる commit も「活動」に数える
active = len(commits_last_7_days) > 0

# OK: 自動で入るものを除く
active = any(not only_touches(c, ".claude/") for c in commits_last_7_days)
```

事例

- 起動 hook が展開物を commit するので、全 commit を数えると「セッションが立った＝稼働」になった。あるリポジトリの7 commit は全部が展開物だった
- 鮮度をファイルの更新日時で測ったら、集計の処理自体でも更新され、全部が最新に見えた

## 日付と時刻

### タイムゾーンを取り違える

when

- 日付・時刻を作る・切り出す・表示する・比べる式を書いている
  - `new Date`
  - `toISOString`
  - `datetime`
  - など
- 時刻を定数で書いている
- など

then

- どのタイムゾーンの値か、比べる相手と揃っているかを確かめる。例:
  - `toISOString().slice(0, 10)` で、日本の朝が前日になる
  - 締めの時刻の直書きが、夏時間でずれる
  - など

事例

- 完了の日付を UTC で記録し、朝の完了が前日に付いた
- 海外の締めの時刻を UTC で決め打ちし、夏時間の切り替えでずれる
- UTC の時刻を JST と読み違えた

## 保存

### 同じ値を2か所に保存する

when

- 値を持つ場所を足している
  - DB・KV・ファイルへの書き込み
  - state の宣言（`useState` など）
  - など
- など

then

- 数え直せる値や同じ値を、別の場所にも持っていないかを確かめる
- 持っていたら、場合に応じて提案する
  - 他から計算できる値（件数、合計、props から作れる state）なら、持たずに使うたびに計算する
  - 別々の入力を1回の書き込みにまとめているなら、入力ごとに分ける

事例

- 日別の完了数を、元の記録とは別に保存していた。完了の操作で更新されず、全日 0 のまま残った
- メモが判定とセットでしか保存されず、判定を戻すとメモまで消えた

### 書き込みの失敗・順序でデータが壊れる

when

- 書き込みに関わる呼び出しを書いている
  - DB への書き込み（`INSERT`、batch）
  - キューへの送信
  - 再試行の設定（`retry`、`max_retries`）
  - など
- など

then

- 失敗・順序・再試行で、他のデータを巻き込んだり失ったりしないかを確かめる。例:
  - 前の書き込みを待たずに、同じレコードへ書く
  - 1件の不正な値で、batch 全体が失敗する
  - 再試行の上限を超えたものの行き先が無い
  - など

コード例

```
// NG: 1件の不正な値で batch 全体が失敗し、再試行の上限で全部捨てられる
await db.batch(records.map(toInsert));

// OK: 先に検証して、入らない値だけを外して記録する
const [ok, ng] = partition(records, isStorable);
await db.batch(ok.map(toInsert));
if (ng.length) log('rejected', ng);
```

事例

- 1件の値が DB の列の制約で拒否され、同じ batch の無関係な記録まで、再試行の上限で捨てられた
- 上限を超えた記録の置き場（dead letter queue）を作ったが、読む処理が無く、24時間で消える
- 同じレコードへの書き込みが、前の書き込みを待たずに並んで起きうる作りだった

### 入力の検証が漏れる

when

- 入力を検証する `if` 文などの条件式や、検証の関数を書いている
- など

then

- 検証を通った値が、保存先や後の処理で本当に扱えるかを確かめる。例:
  - `Number.isInteger(1e300)` は通るが、INTEGER の列に入らない
  - `Date.parse` で 2/30 が通る
  - 形式だけを見て、項目どうしの関係（時刻の前後）を見ていない
  - など

事例

- `Number.isInteger` を通った巨大な値が、D1 の STRICT な INTEGER 列で拒否された
- 記録の時刻と、その記録が参照した値の時刻の前後を検査していなかった

### 保存済みのデータの形を変えて矛盾させる

when

- 保存済みのデータの形を変えている
  - `migrate` などの移行の関数
  - 保存する型・スキーマの変更
  - など
- など

then

- すべての状態について、移行後の値の組み合わせが矛盾しないかを確かめる
- 使える環境なら、版を持って移行できる仕組みも提案する（例: zustand の `persist` の `version` と `migrate`）

事例

- データの形を移行したら、一部の状態で矛盾した組み合わせができた

### 成功する前に、回数や枠を減らす

when

- カウンタ・残り回数・1日の枠を減らす式（`count--`、`remaining -= 1`）を書いている
- など

then

- 減らすのが、実際に成功した後かを確かめる
- そもそも減らす式を書かない形を提案する。使った回数は、実際に出した・送った記録から数える

コード例

```
// NG: 出せる候補が無くても、今日の枠を使ってしまう
usedToday += 1;
const item = pickCandidate();

// OK: 出せたときだけ枠を使う
const item = pickCandidate();
if (item) usedToday += 1;
```

事例

- 候補のリストから1日1件を出す機能で、出す候補が無い日にも、その日の1件分の枠を使っていた。そのため、その日に新しく足した候補が出なかった
