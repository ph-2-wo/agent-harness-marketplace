# 手順書の観点

## 手順書

### 他の指示と食い違う

when

- 次のものを書いている
  - コマンドの例・使用例
  - ルールの節
  - など
- など

then

- 他の指示と矛盾していないか、同じことを書き直していないかを確かめる

事例

- 手順書に、別の指示が禁止した操作のコマンド例が残り、食い違っていた
- 別の指示を言い換えた節が CLAUDE.md に残り、元の指示が変わったときに片方だけ古くなった

### 名前・日付・記録への参照を書く

when

- 手順書や観点ファイルの本文に、次のものを書いている（観点の when / then を含む）
  - 一緒に働く人・エージェントの名前
  - ユーザーの名前
  - 日付
  - 何回目か・その時点の結果（「2回目」「使った結果」など）
  - 作業の記録のファイルを読ませる・根拠として指す記述
  - 書いた時の会話でしか通じない短い呼び名（中身が落ちる言い換えラベル）
  - など
- など

then

- 突き返す
- 名前は、誰にでも当てはまる言葉（「ユーザー」「エージェント」など）に直させる
- 日付と記録への参照は消させる。指示に要る中身があれば、その中身を指示として書かせる
- 短い呼び名は、指している中身に書き直させる

事例

- チェックリストの項目の理由に、ユーザーの名前を書いた
- 手順書の案から日付だけを消し、「試し2回目」や「使った結果」の列を残した
- スキルの手順に、空のリポジトリを作る人としてユーザーの名前を書き、観点の事例には起きた場所としてエージェントの名前を書いた

### 根拠の無い制約を書く

when

- 「できない」「人に頼む」「申請が要る」と書いている
- など

then

- 試した結果が根拠として示されているかを確かめる

事例

- 手順書に「申請が要る」と書いていたが、実際は要らなかった

### 定時実行が古い状態で動く

when

- 定時実行・予約で起きるセッションが読む手順を書いている
- など

then

- 先頭で最新の状態を取り込んでいるか、遅れて動いても意味のある処理かを確かめる

事例

- 定時実行の手順の先頭に、最新化の手順が無かった
- 起きなかった予定を後からまとめて実行し、朝に動くはずの定時実行が半日遅れで動いた

### 文章だけで禁止する

when

- 「〜しない」「〜は禁止」を足す・直している
- など

then

- 破られたときの被害が大きいなら、`permissions.deny` や hook で止めさせる

事例

- ある git 操作の禁止を文章で書いただけで、定時実行が毎回その操作をしていた。`permissions.deny` で止めた

### スキルの description に中身を書く

when

- `SKILL.md` の `description:` の行を足す・直している

then

- `skill-review` の手順1の基準で description を確かめる

事例

- 本文に節を足すたびに description にも項目を足し、description が本文の目次になった
