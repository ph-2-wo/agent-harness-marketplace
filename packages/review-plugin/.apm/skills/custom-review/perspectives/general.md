# 全ファイル共通の観点

## 失敗の扱い

### 失敗を握りつぶす

when

- 失敗しうる呼び出しを書いている
  - 外部コマンド・サブプロセス
  - API・ネットワーク
  - ファイル・DB の読み書き
  - パース・型変換
  - など
- エラーを扱う構文を書いている
  - `try` / `catch` / `except`
  - シェルの `||`・`2>`・`>/dev/null`
  - など
- など

then

- 失敗が、呼び出し元や利用者から見えなくなっていないか確かめる。例:
  - `|| true` や空の `catch` の後で、結果を0件として扱う
  - `>/dev/null 2>&1` と `exit 0` 固定で、失敗しても成功と同じ終わり方をする
  - 元のエラー文を捨てて、汎用の文だけを返す
  - など
- 見えなくなっていたら、場合に応じて提案する
  - 止めてよい処理なら、止めてエラーとして出す
  - 止めない設計なら、終了コードとエラー文をログに残す
  - 利用者が普段見る画面がある処理なら、止まったことと最終成功時刻を画面に出す

事例

- Stop hook が `python3 - <<'PY'` の中で `json.load(sys.stdin)` を呼んでいた。stdin が heredoc に取られて読み込みが失敗し、それを `except` が握りつぶし、`2>/dev/null` で例外も見えなかった。判定が一度も動いていなかった
- 起動 hook が `apm install >/dev/null 2>&1` の後に `exit 0` で終わり、失敗しても誰も気づけなかった。ログに終了コードを残す形に直した
- 集計スクリプトで git が失敗したのを「commit ゼロ」と読んだ。終了コードを検査するように直した
- 使用量ウィジェットが認証の失敗で `paused = true` になり自動更新が止まったが、画面はいつもどおりで気づけなかった

## 外部のツール・サービス

### 一覧・件数を既定の範囲だけで取る

when

- 外部の API・CLI・MCP ツールで、一覧や件数を取る呼び出しを書いている
  - `list_*` のようなツール
  - `git log`
  - `per_page`・`limit` を取る API
  - など
- など

then

- そのツールの既定の範囲で取りこぼさないか確かめる。例:
  - 既定ブランチしか見ない
  - 1ページの上限件数で切れる
  - など
- 取りこぼすなら、全件を取る指定かページ送りを入れさせる

事例

- リポジトリの活動を集計するのに `list_commits` を使ったら、既定ブランチ（`main`）しか返さず、未マージのブランチで進んでいた作業を「活動なし」と誤報した。100件で切れて活動日も少なく数えた
- issue のコメントを読むときにページ指定を誤り、一部しか読んでいなかった

### 初めて使う外部ツールの挙動を確かめずに頼る

when

- 外部のコマンド・API・ツールの呼び出しを新しく書いている、またはサブコマンド・オプションを変えている
- コメントに「未確認」「のはず」と書いている
- など

then

- 頼っている挙動を、公式ドキュメントかソースで確かめたかを問う。例:
  - 似た役割のサブコマンドの違い（`apm install` と `apm update`）
  - イベントやデータが届く条件
  - 公式ドキュメントに無い内部形式
  - など
- 確かめられないなら、前提が外れたときに気づけるログか警告を入れさせる

事例

- 起動 hook で `apm install` を使っていた。これは lock の版を再現するだけで更新しないので、古い展開物で新しい版を上書きしていた。`apm update` に直した
- 通知の hook が、公式ドキュメントに無い会話記録の行を最大120秒待って読んでいる。形式が変わると壊れる
- Slack のスコープを、使う API を確かめずに2回に分けて足した

### 実行される環境に無いものに依存する

when

- 手元と別の場所で動くコードを書いている
  - hook
  - cron・定時実行
  - 別プロセス（ウィジェットなど）
  - 別コンテナ
  - など
- 外部のものを参照している
  - コマンド
  - パス
  - 環境変数
  - ログイン状態
  - など
- など

then

- その依存が、実際に動く環境にあるかを確かめる。例:
  - OS 標準でないコマンド（`rclone`、`jq`）
  - 展開されるとは限らない変数（`${CLAUDE_PLUGIN_ROOT}`）
  - 手元にしか無いパス（`~/.claude/`、絶対パス）
  - 空の状態から始まる初回
  - など
- 無いことがありうるなら、無いときの扱いを書かせる

事例

- 同期スクリプトが `rclone` を前提にしていた。別の利用者のコンテナには無く、毎回失敗して同期されなかった。作った側のコンテナには古い `rclone` が残っていたので、作った側では気づけなかった
- 同じスクリプトが、保存先が空だと手元のディレクトリを作らず、最初の1回が永久に始まらなかった
- 使用量ウィジェットが、アプリ内のログイン状態を引き継がない別プロセスで動き、自動更新が止まった。調査の時点で「未確認」と書いたまま実装していた
- hook の command に書いた `${CLAUDE_PLUGIN_ROOT}` が、配布先では展開されなかった

## 外から来た値

### 外から来た値をそのまま使う

when

- 外から来た値を読んで使っている
  - リクエスト・ペイロード
  - 環境変数
  - 利用者の入力
  - 読み込んだファイルの中身
  - など
- など

then

- 値の中身しだいで壊れないか確かめる。例:
  - `obj[key]` に `__proto__` が来る
  - ヘッダーや URL に連結した値に、余計な部分が入っている
  - 埋め込んだ値に `</script>` が入る
  - など
- 型やスキーマで防げるなら、型で防ぐ形を提案する。防げないなら検証かエスケープを入れさせる

事例

- 環境変数の値にヘッダー名まで入っていて、hook がそこへさらに同じ名前を前に付けたため、リクエストが 302 で失敗した
- 配布ページの `<script type="text/plain">` に、`</script>` を含むソースを埋めて途切れた。別の作り手が同じ形のページを作ったときにも、同じことが起きた
- 外部の文字列で `obj[key]` を引く箇所に、最初から `Object.hasOwn` を入れて `__proto__` を防いでいた（防げていた例）

## 正本

### 同じ事実を2か所に持つ（SSoT）

when

- always（すべての差分）

then

- 正本を1つにする（SSoT）。同じものが他の場所にないか、既にある正本から導けないかを確かめ、あれば1か所から参照させる
- 同じ事実の例:
  - コード（関数・変数・定数）
  - データ（DB などのデータ実体・スキーマ）
  - ドキュメント
  - など

事例

- 利用状況のダッシュボードで、同じ絞り込みが2つの SQL に別々に書かれ、「起動」の数と「合計時間」で対象のセッションがずれた
- 台帳と評価ツールが同じ換算の式を別々に持ち、片方だけ誤っていた
- 巡回の対象のリポジトリを別のファイルに手で書き、各リポジトリの README と二重管理になった。リポジトリの一覧から導く形に変えた

### 名前を変えたもの・消したものへの参照が残る

when

- 名前を変える・消す
  - ファイル
  - 関数
  - skill
  - 設定キー
  - 規則
  - など
- など

then

- 型やコンパイラで検出できるなら、そちらに任せる
- 検出できないものは、旧名や消したものへの参照が残っていないかを探す。例:
  - ドキュメント
  - 設定ファイル
  - 文字列で書いたパス
  - 配布先に展開されたファイル
  - など

事例

- 通知スクリプトを改名したが、hook の定義（`notify.json`）が旧名を指したままだった
- 上流で hook を消しても、APM の掃除の穴で配布先の `settings.json` に登録が残った
- rebase を禁止した後も、起動設定6本に `git pull --rebase` が残っていた

## 名前

### 名前だけでは指すものが1つに決まらない

when

- 名前を付ける・使う（変数・関数・フィールド・ファイル・ディレクトリ・記号・略語・手順書の用語と見出しなど）

then

- その名前だけを読んで、何を指すかが1つに決まるかを確かめる
- 決まらないもの（type・group・data のような一般語、1文字の記号、連番だけの名前、その作業の中でしか通じない略語など）は、指すものが分かる名前にする
- 同じ語を、別の意味で使っている所が無いかを探す
- 英語の名前や技術用語を、一般の日本語に訳して名前にしない

## 差分の中身

### 意図しない変更が混ざる

when

- 変更の目的と結びつかない行・ファイルが差分にある
- など

then

- 目的と関係ない変化は、戻すか別の変更に分けさせる。例:
  - 表記やキー順だけの変化
  - ファイルモードの変化
  - 生成物（`__pycache__/` など）
  - 依頼に無い分岐・機能
  - など

事例

- JSON を機械的に書き換えたら、エスケープの表記まで変わった。1行の変更が3 commit になった
- GitHub の API 経由で push したら、スクリプトの実行ビットが落ちた
- `__pycache__/*.pyc` を commit していた
- 抜け道をふさぐ変更に、依頼に無い判定の変更まで同梱して、revert になった

### 判定の条件を実例で確かめずに変える

when

- 違反・異常・要注意を判定する条件を、足す・変える・削る
  - `if` 文などの条件式
  - 閾値
  - 正規表現
  - 手順書の「〜なら違反」
  - など
- など

then

- 正常と分かっている例と、過去の実例に当てた結果を求める

コード例

```
# NG: 条件を変えて、そのまま報告に使う
def is_stale(repo):
    return days_since_last_commit(repo, branch="main") > 3

# OK: 正常と分かっている例に当ててから使う
assert not is_stale(repo_worked_on_yesterday)   # 未マージのブランチで作業が進んでいたリポジトリ
```

事例

- 活動の集計の初回で、前日にも作業が進んでいたリポジトリを「要注意」に出した。動いていると分かっている例に当てていれば防げた
- 引用を照合するスクリプトが12件を検出したが、10件は誤検出だった。正規表現で前後関係を読んでいた
- 監査の判定ルールが誤っていて、正しい記録を違反と報告した
