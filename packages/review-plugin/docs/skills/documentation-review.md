# documentation-review

ドキュメントが、その文書の責務に合う情報を、適切な場所と時間軸で伝えているかレビューする。

## 解決する課題

ドキュメントは、置き場所と時間軸を間違えると必ず腐る。
README に「現時点の課題リスト」や「移行中の状態」を書けば、対象が変わるたびに嘘になる。
設定の詳細を別ファイルから書き写せば二重管理になる。

一方で、更新コストを嫌って必要な情報まで削ると、読者が判断できない文書になる。
削りすぎも問題として扱うのがこの skill の特徴。

## 概要

文書の責務を `Reader/action × Subject scope × Time perspective` の 3 要素で捉える。
特に時間軸を stock（現在の仕様・使い方）と flow（変更・経緯・移行）に分け、
stock 文書が経緯や TODO を抱えていないか、flow 文書が現行仕様を複製していないかを見る。

そのうえで記述ごとに、必要性・正本の所在・時間軸の適合を判定し、
最後に文書全体で completeness（読者が目的を達成できるか）と maintenance（責務外の変更で更新が発生しないか）を検算する。

文書自体は編集せず、actionable な指摘だけを返す。

## 利用場面

開発変更に README、設計書、runbook、ADR、migration guide などの追加・更新が含まれる場合のレビュー。
