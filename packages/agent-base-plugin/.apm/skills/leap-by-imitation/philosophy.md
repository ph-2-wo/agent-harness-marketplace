# なぜ改善を重ねても届かないのか

この文書は、スキル `leap-by-imitation` の背景にある思想書である。
手順は `SKILL.md` にある。
ここには、その手順がなぜ要るのかを書く。

## 小さな修正は、足場を抜いて上に積む

ジェンガを思い浮かべるとよい。
ブロックを1本抜いて上に積むたびに、塔は高くなる。
けれど、その1本は塔を支えていた足場から抜いたものだ。
高さが伸びるほど、下はスカスカになっていく。

パッチワークやマイナーチェンジは、これと同じ形をしている。
指摘された箇所を直すと、その箇所は良くなったように見える。
けれど直すたびに、元の形を支えていたもの（なぜその形だったのか、全体の釣り合い）が少しずつ削られる。
1回ごとのズレは小さく、意味も持たないので、気づけない。
最初はうまく行っているように見える。
ズレが積み重なったある時点で、塔はまとめて倒れる。

## 前の成果物から繰り返すと、毎回の解釈に全部を賭けることになる

よくある繰り返し方は、前回うまく行った成果物に少し情報を足して、次を作らせるものだ。
これは、そのときどきのエージェントの解釈に、ほぼ全部を賭けるやり方になる。
前回の成果物がなぜ良かったのかは、成果物の中には書かれていない。
次のエージェントはそれを知らないまま、足された情報に合わせて形を変える。
その変え方が、毎回少しずつ本質から外れる。
外れた成果物が、また次の土台になる。

## 傾いた塔に、目の前のブロックを足しても戻らない

崩れかけた塔は、上にブロックを足しても立て直せない。
足すほど傾きは大きくなる。
立て直すには、視点を後ろに下げて、全体の骨組みと形から設計し直す。

このスキルの言う飛躍は、この設計し直しのことだ。
今の形を少し変えるのではなく、今の形の前提から作り直す。
ただし、今の塔だけを見ながら設計し直すと、同じ形をまた作ってしまう。
だから、他の実例（種）から骨組みを借りる。

## 兆候

次のどれかに当たるなら、塔を積み増している。

- 指摘のたびに、指摘された箇所だけを変えている
- 直した箇所の近くに、また指摘が来る
- 前に直したことと、今直していることが食い違う
- 元の形がなぜ良かったのか、もう説明できない

## 建築にも同じ構造がある

ソフトウェア設計の論文 Big Ball of Mud（Brian Foote, Joseph Yoder）は、場当たりの増築で崩れたシステムを、無計画に建て増したスラム（shantytown）にたとえている。
そこまで崩れると、全部を壊して建て直す（RECONSTRUCTION）しかない。
そのとき持ち出せるのは、経験の底にあるパターンだけだと書かれている。
