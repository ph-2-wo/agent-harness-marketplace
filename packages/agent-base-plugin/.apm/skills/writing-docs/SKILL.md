# 恒久ドキュメントの書き方

README のような**恒久ドキュメント**（対象が存在する限り読まれ続ける文書）には、
**その対象が存在する限り変わりづらいことだけ**を書く。

## 書かないもの

- **正本が他にある情報を書き写さない**: 設定の詳細（別ファイルに規則があるならそれを参照する）、
  ディレクトリ構成（構成そのものが正本であり、コマンドで読める）。書き写すと二重管理になりズレる。
  構成を示すなら、変わりにくいディレクトリか、特に重要なファイルだけに絞る
- **フロー情報を書かない**: 「未確認の課題リスト」「現時点の顔ぶれ」など、時間とともに変わる情報。
  恒久ドキュメントに置くと必ず腐る
  - 日付や経緯の括弧（「YYYY-MM-DD に〜と言われた」）は手順書に書かず、記憶の側に置く
- **個数を書かない**: 「エージェント3体」のように数を書くと、**それ以上増やしてはいけない前提**が生まれる。
  「複数」と書く
- **余計な解釈・見積もりを書かない**: 「数か月〜数年かかる」のような、依頼者が言っていない前提は
  ミスリードになる

**説明のための文章は、恒久ドキュメントにしない**。誰かに現状を説明するために書く文章は、
その時点でだけ必要な**一時資料**（時点付き）として作る。README に混ぜると、
説明の役目を終えた後も残って腐る。

## 削るときの歯止め

**「正本が他にある＝重複だから消す」を機械的に適用しない**。重複してよいかは文字列が同じかではなく、
**その文書の読者が、その文脈でその情報を必要とするか**で決まる。目的が違う文書なら
同じ情報が複数箇所にあってよい。特に **CLAUDE.md と instruction（`.claude/rules/`）は
Agent がゼロショットで必ず読み込む**という他の文書にない性質があるため、
「README に書いてあるから CLAUDE.md や instruction からは消す」は成立しない
（README は読まれない可能性があるが、この2つは必ず読まれる）。

**具体的な数値・固定値を「抽象度を上げる」名目で落とさない**。「上限2回」のような値は、
意図的な指定であることが多い。抽象化すると指定そのものが消える。
