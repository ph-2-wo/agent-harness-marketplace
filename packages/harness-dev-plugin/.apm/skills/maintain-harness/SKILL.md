# maintain harness

## 原因特定

### 1. 失敗、不適切な行動の原因特定

ハーネスのせいにする
その場のエージェントとユーザーのせいにしない

以下に分類する
複数当てはまる場合は主要因と補足にわける

- そもそも記載されていないので知らなかった
- 手順が具体的でないのでわからなかった
- 利用タイミングの誘導が不十分なので使えなかった
  - 直し先は、description の「いつ使うか」の言い方か、その場面の手前で使われるスキルの手順（そこから呼ぶ）
- 別の指示とコンフリクトしていて優先度を下げてしまった

## 2. 対処箇所の選定

`harness-placement` を使って、部品の種類と置き場所を決める。

## 3. 改善の大枠方針の決定・承認

「単純な改善」か「スクラッチからの開発」に分類する

## 単純な改善の場合

### 4. 最小化 Review

今思いついている方針を `document-minimization-review` にかけて最小化して提案する
承認されたら完了

## スクラッチからの開発の場合

### 4. 改善の大枠方針の設計

設計をする

- まず素朴な改善方針を2〜3行で考える
  - 「こう考えてくれれば良さそう」
  - 「この情報があれば良さそう」
- この段階では手順として全く成立してなくて良い
  - 成立させるための書き足しをここでしない

### 5. Review 1 手順化

`harness-proceduralization` を使用して今の考えを具体に落とす

### 6. Review 2 最小化

`document-minimization-review` を使用して本質的に必要な記述に絞る

### 7. 方針の決定

Reviewをもとに方針を決定
`zero` でユーザーに説明
ユーザーに承認されたら完了

## 承認後

承認された方針で直したら、その差分を `custom-review` にかける。
