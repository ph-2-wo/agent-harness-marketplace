# 既にあるテストを組み直す

組み直した後の形は `test-design` スキルに従う。
このスキルは、今のテストからそこへ移す手順を扱う。

## 1. 今のテストの状態を調べる

組み直す前に、次を調べて、対応表（手順2）の先頭に書く。

- 全テストを流したコマンドと並列数、ファイルごとと全体の実行時間
- 通ったテストと落ちたテスト
- 固定の wait の数と合計の時間。`sleep`・`waitForTimeout`・`setTimeout` を grep し、helper の中も数える
- モックの置き場所と数。本体の関数や組み込みの関数を差し替えている所

落ちたテストがあれば、組み直しを始める前にユーザーに扱いを確かめる。

## 2. 旧テストの項目を分けて、対応表を作る

assertion を1つずつ、次のどれかに分ける。

| 分類 | 移す先 |
| :-- | :-- |
| ロジックを画面経由で確かめている | ロジックの部品の入力と出力（モックなし） |
| 外部との受け渡しを確かめている | 部品の入力と出力（外部との境界のモックだけ） |
| 画面でしか確かめられない | e2e（ユーザーフロー単位） |
| 別の項目と同じ仕様を確かめている | 1つに寄せ、残りは消す |
| 実装の内部を確かめている | 見える状態の確認に置き換えるか、消す |
| 必ず通る、または守る仕様が読み取れない | ユーザーに確かめる |

分けた結果を、そのまま対応表にする。
列は「旧項目 / 分類 / 行き先 / 消した理由」にする。
対応表は組み直しの PR の説明に載せ、リポジトリには残さない。

assertion が数十を超えるときは、サブエージェントに分けさせ、件数と代表の所在だけを返させる。

## 3. 本体の形を整え、新しいテストを書く

本体を `test-design` の「本体を、外部との境界でだけモックを差し込める形にする」に合わせる。
本体の公開の形（ファイルの数・読み込み方）が変わるときは、先にユーザーに確かめる。
整えた後に旧テストを流し直し、手順1と同じ結果になることを確かめる。

新しいテストは `test-design` に従って書く。
旧テストの seed や helper は流用しない。

書き終えたら、対応表の行き先に、新しいテストのファイルとテスト名を埋める。

消してよいのは、重複と実装の内部を確かめる項目だけ。
消したことで確かめられなくなる振る舞いがあれば、対応表に書く。
それ以外を消すときは、先にユーザーに確かめる。

## 4. 強さが落ちていないかを確かめる

対応表のうち、次の項目を選ぶ。

- 期待値・待ち時間・前提のデータを旧テストから変えた項目
- 別の項目に寄せた項目

それぞれ、旧テストが落ちていた実装の変更で、新しいテストも落ちるかを、対応表と差分を読んで確かめる。
読んで決まらないものだけ、次の手順で確かめる。

1. 実装を1行だけ変えて、その項目が落ちることを見る
2. 変えた行を元に戻す
3. `git diff` で、変えた跡が残っていないことを確かめる

## 5. 前後を比べる

- 手順1と同じコマンドと並列数で、全テストを3回流す
- 1回でも落ちたテストがあれば、不安定として直す
- 実行時間を、手順1の数字と並べて PR の説明に書き、ユーザーに報告する
