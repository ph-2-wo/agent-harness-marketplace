# テストを最初から良い設計で書く

良いテストは、実装を変えても直さずに済み、仕様が壊れたときだけ落ちる。

## 守る仕様を書き出す

テストを書く前に、守る仕様を箇条書きにする。
仕様は、ユーザーや呼び出し側に見える振る舞いで書く。
「◯◯を入れたら△△が返る」「◯◯を押したら△△が表示される」の形にする。
「この関数がこの関数を呼ぶ」のような実装の手順は書かない。
書き出した仕様は、そのままテストの名前にする。

## 本体を、外部との境界でだけモックを差し込める形にする

- 外部（API・db・ストレージ・ファイルなど）を呼ぶ所を、テストのときにモックに差し替えられるようにする。以下、ここを外部との境界と呼ぶ
- 境界をどこにどう置くか（1か所に集めるか、gateway・client・adapter などの呼び名）は、そのリポジトリの構成に合わせる
- ロジックを DOM と外部から分け、引数で受け取って値を返す形にする

テストを書く前に、この形になっているかを見る。
なっていなければ、テストより先に本体の形を直す。
直す範囲が、今回テストする仕様に触れる所を超えるときは、先にユーザーに範囲を確かめる。

## 仕様ごとにテストレベルを決める

テストレベルは、1つのテストが動かす範囲の大きさ。
書き出した仕様の1つずつに、次の表でテストレベルを決める。

| 仕様が確かめられる所 | テストレベル | 動かすもの |
| :-- | :-- | :-- |
| 関数・module（DOM に触れないもの） | 単体テスト | その関数・module を、引数と返り値で |
| 画面のコンポーネント1つ（操作・表示・ブラウザの振る舞い） | コンポーネントテスト | そのコンポーネントを子と一緒に描き、props や上から渡す値（context など）を変える |
| 複数のコンポーネントにまたがる挙動（画面の移り変わり・コンポーネントの間で共有する状態など） | 統合テスト | 画面全体を描く |
| 外部との境界をモックせず、動かしたアプリ全体でしか確かめられないもの | e2e | ユーザーフロー単位で |

1つの仕様は、それを確かめられる一番小さいテストレベルで試す。
表は、上の行ほど小さい。
同じ仕様を別のテストレベルで重ねて試さない。

外部にも DOM にも触れないロジックは、モックなしで試す。
外部との受け渡し（保存・読み込み・エラー・リトライ）は、外部との境界のモックを差し込んで試す。

## テストの単位を、部品の入口で切る

テストの単位は、呼び出し側が使う入口にする。
入口は、単体テストでは公開された関数・module、コンポーネントテストでは公開されたコンポーネント、統合テストと e2e では画面の操作1つ。
入口の中の関数を1つずつテストしない。
1つの入口を、入力（コンポーネントなら props や上から渡す値）と seed を変えて何通りも動かす。
ケースごとに、入口の中身を差し替えない。

例外として、入力と期待値を表で並べるのが自然な部分（パーサー・計算式など）は、その部分を単位にした単体テストにしてよい。

## 外部との境界のモック・seed・helper を先に作る

外部との境界のモックは、確かめる仕様に合わせて、次のどちらかにする。
どちらでも、呼び出しの記録（呼ばれた回数・引数）を assert に使わない。

| 確かめる仕様 | モック |
| :-- | :-- |
| 保存したものを、読み戻して確かめる | Fake（簡略にした動く実装を持つモック） |
| 決めた値・エラー・遅延・空を返させて、確かめたい状態にするだけ | Stub（決めた答えを返すだけのモック）と Fake のうち、書きやすい方 |

テストを書き始める前に、次を、各テストから共通に使える形で作る。

- 外部との境界のモック。Fake は、保存したものを読み戻せ、エラー・遅延・空も返せる形にする。外部の振る舞いのうち、Fake に写すのは、テストが確かめる仕様に要る分だけにする
- seed。各テストの前提のデータを、Fake に入れるか Stub に返させる形で用意する
- helper。操作や読み取りの繰り返しをまとめる

モックは、外部との境界のモックだけに限る。
本体の関数や組み込みの関数は差し替えない。
例外は時間で、待ち・debounce・リトライ・長押しなどは、テストの道具の fake timers で進める。

## 各テストの書き方

### 各テストは自分の seed から始める

前のテストが作った状態を前提にしない。
前提の状態を UI の操作で作らない。
UI を操作するのは、そのテストで試すフローだけにする。

### 固定の wait を書かない

sleep・waitForTimeout のような、時間を決め打ちした待ちを書かない。
状態になるまで待つ assertion を使うか、fake timers で進める。

### assert するのは出力と見える状態だけ

呼び出し回数・内部の変数・private な関数は assert しない。
保存の仕様は、Fake から読み戻した内容を assert して確かめる。

### 必ず通る assertion を書かない

値があることだけを見る assertion（`toBeDefined()` だけなど）や、条件分岐の中に置いた assertion を書かない。
エラーを握りつぶして（`.catch(() => {})` など）先に進めない。

### 期待値は仕様から書く

期待値は、書き出した仕様から書く。
実装を動かして出た値を、そのまま期待値に写さない。
