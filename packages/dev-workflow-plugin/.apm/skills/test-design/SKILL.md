# テストを最初から良い設計で書く

良いテストは、実装を変えても直さずに済み、仕様が壊れたときだけ落ちる。

## 守る仕様を書き出す

テストを書く前に、守る仕様を箇条書きにする。
仕様は、ユーザーや呼び出し側に見える振る舞いで書く。
「◯◯を入れたら△△が返る」「◯◯を押したら△△が表示される」の形にする。
「この関数がこの関数を呼ぶ」のような実装の手順は書かない。
書き出した仕様は、そのままテストの名前にする。

## 本体を、外部を gateway に集めた形にする

- 外部（API・db・ストレージ・ファイルなど）を呼ぶ所を、gateway として1か所に集める
- テストのときに gateway の実装を差し替える口を、1か所に用意する
- ロジックを DOM と外部から分け、引数で受け取って値を返す形にする

テストを書く前に、この形になっているかを見る。
なっていなければ、テストより先に本体の形を直す。
直す範囲が、今回テストする仕様に触れる所を超えるときは、先にユーザーに範囲を確かめる。

## 仕様ごとに layer を決める

書き出した仕様の1つずつに、次の表で layer を決める。

| 仕様が確かめられる場所 | layer |
| :-- | :-- |
| 外部にも DOM にも触れないロジック | 部品の入力と出力（モックなし） |
| 外部との受け渡し（保存・読み込み・エラー・リトライ） | 部品の入力と出力（gateway のモックだけ） |
| 画面でしか確かめられないもの（操作・表示・ブラウザの振る舞い） | e2e（ユーザーフロー単位） |

1つの仕様は、1つの layer でだけ試す。
同じ仕様を別の layer で重ねて試さない。

## テストの単位を、部品の入口で切る

テストの単位は、呼び出し側が使う入口（公開された関数・module・画面の操作1つ）にする。
入口の中の関数を1つずつテストしない。
1つの入口を、入力と seed を変えて何通りも動かす。
ケースごとに、入口の中身を差し替えない。

例外として、入力と期待値を表で並べるのが自然な部分（パーサー・計算式など）は、その部分を単位にした unit test にしてよい。

## gateway のモック・seed・helper を先に作る

テストを書き始める前に、次を共通の1か所に作る。

- gateway のモック。呼び出しの記録ではなく、状態を持つ fake にする。保存したものを読み戻せ、エラー・遅延・空も返せる形にする
- seed。各テストの前提のデータを、gateway のモックに入れる形で用意する
- helper。操作や読み取りの繰り返しをまとめる

モックは gateway のモックだけにする。
本体の関数や組み込みの関数は差し替えない。
例外は時間で、待ち・debounce・リトライ・長押しなどは、テストの道具の fake timers で進める。

## 各テストの書き方

### 各テストは自分の seed から始める

前のテストが作った状態を前提にしない。
前提の状態を UI の操作で作らない。
UI を操作するのは、そのテストで試すフローだけにする。

### 固定の wait を書かない

sleep・waitForTimeout のような、時間を決め打ちした待ちを書かない。
状態になるまで待つ assertion を使うか、fake timers で進める。

### assert するのは出力と見える状態だけ

呼び出し回数・内部の変数・private な関数は assert しない。
保存の仕様は、gateway のモックから読み戻した内容を assert して確かめる。

### 必ず通る assertion を書かない

値があることだけを見る assertion（`toBeDefined()` だけなど）や、条件分岐の中に置いた assertion を書かない。
エラーを握りつぶして（`.catch(() => {})` など）先に進めない。

### 期待値は仕様から書く

期待値は、書き出した仕様から書く。
実装を動かして出た値を、そのまま期待値に写さない。
